# Reactor X2

`reactor_service.py` plus `templates/reactor.html` are the one substantial
addition this fork makes to upstream `ugv_rpi`. The page shows the rover's
live camera and, beside it, the same view re-generated by the `xmax/x2` model
according to a text prompt — while still driving the rover.

## What X2 actually does

**X2 is a character/object insertion model, not a world-replacement model.**
This is the single most important thing to know before writing a prompt, and
it is not obvious from the API:

- *"a large fluffy orange tabby cat sitting on the floor in the middle of the
  room, photorealistic"* → a correctly scaled, correctly lit cat with its own
  shadow, inserted into the real scene.
- *"dense forest with trees and nature"* → a near-identity re-render of the
  real room. No forest.

Environment and style prompts are **silently** a no-op: `set_prompt` returns
ok, `/api/reactor/health` shows the prompt as set, frames keep flowing, and the
picture just looks slightly re-textured. Prompt for a subject to insert, not a
world to replace. `templates/reactor.html`'s presets are subjects for this
reason.

An optional **reference image** supplies the character or object to insert.

## Session model

X2 is a persistent streaming session, not request/response. The client
publishes a continuous `source` track; the model streams edited frames back on
`main_video` at its own block cadence, independent of how fast frames are
pushed. So the interface is push/pull — `push_frame()` in, `get_latest_output()`
out — never process-one-get-one. There is no `start` command: X2 generates as
soon as a prompt and frames both exist.

Two invariants the implementation exists to maintain, both learned from a
failure where the page showed a frozen frame for many minutes while health
cheerfully reported `connected: true`:

**A publish does not survive the session leaving `ready`.** Sessions drop and
re-establish on their own, and on the way back the `source` track is
unpublished and the prompt is cleared — every `push_frame` then raises
`INVALID_STATE` and no output is ever produced again. Publishing therefore runs
from the `on_status` handler on every return to READY, re-sending the prompt
with it. Do not publish once at connect.

**Liveness must be derived, never cached.** A `connected` bool set once at
connect stays true forever after the session dies. Both `connected` and the
freshness of the last frame are computed at read time
(`status == READY and track.published`), and output older than `STALE_AFTER_S`
(3s) is **withheld** rather than re-served — serving the last good frame
forever is exactly what makes a dead session look like a working one. The same
rule applies to the prompt: `self.prompt` is assigned only *after* the model
accepts it.

## Prompt length

`set_prompt` has a hard server-side cap of **1000 characters**. Over that the
whole command fails and the *previous* prompt silently stays in effect. The
length is checked client-side up front, so an over-long prompt returns HTTP 400
immediately instead of costing a round trip, and never leaves `self.prompt`
holding something the model rejected. The page shows a live character count.

## Latency — do not drive by this view

Measured on the rover: throughput keeps up 1:1 (camera pushes ~12fps, X2
returns ~11.5–12.5fps; first edited frame ~2s after a prompt is set). But
**glass-to-glass content latency is ~5–6s and drifts upward** — 6.1s → 9.1s
over 90s of continuous streaming. Drive by the live pane, never the edited one.

`reset()` is the only lever on that drift: it tears the session down and
rebuilds it, starting from an empty pipeline and a cleared cache. It is exposed
as the page's **Reset** button.

## HTTP API

| Endpoint | Method | Notes |
| --- | --- | --- |
| `/video_feed_reactor` | GET | MJPEG of the edited stream. Falls back to the raw camera when there is no recent model output. |
| `/api/reactor/prompt` | POST | `{"prompt": "..."}`. **400** if over 1000 chars, **502** on a model/transport error. |
| `/api/reactor/reference-image` | POST | multipart, field `image`. Saved next to `app.py` as `reactor_reference_<name>` (gitignored), then uploaded as a `FileRef`. |
| `/api/reactor/reset` | POST | Rebuild the session, keeping the prompt. ~10s. |
| `/api/reactor/disconnect` | POST | Drop the session and free the model slot. |
| `/api/reactor/connect` | POST | Bring a dropped session back. |
| `/api/reactor/health` | GET | See below. |

### `/api/reactor/health`

```json
{
  "reactor_connected": true,      // derived: READY *and* source published
  "prompt": "...",                // only what the model accepted
  "frames_processed": 1234,
  "reference_image": "cat.png",
  "output_fps": 12.1,
  "push_fps": 12.0,
  "output_age_s": 0.08,           // null when nothing has arrived
  "status": "ReactorStatus.READY",
  "published": true,
  "max_prompt_chars": 1000
}
```

**Judge liveness by `output_age_s`, not `output_fps`.** The fps figure is a
rate over the last 60 output timestamps with no age check, so a session whose
newest frame is 36 seconds old still reports a healthy ~12fps.

## The mock

With no `REACTOR_API_KEY`, `init_reactor()` builds `MockReactorX2` instead: a
passthrough that returns whatever was pushed. The page works end to end, the
"edited" view is just the camera. This is what you are seeing if the Reactor
pane looks identical to the live one and health reports `"status": "mock"`.

> `MockReactorX2` is defined **before** `RealReactorModel` and duplicates
> several method names (`set_prompt`, `set_reference_image`, `get_stats`). A
> single-occurrence search-and-replace anchored on one of those lands in the
> mock. Anchor on text unique to the target class.

## The control page

`templates/reactor.html` is served as a static file by `app.py`'s catch-all
route, so it is **not** Jinja-rendered — no `url_for`. It contains:

- split live / edited video (`<img>` tags, both required — see
  [architecture.md](architecture.md#video-pipeline));
- real WASD drive and gimbal control over the same `/json` and `/ctrl` Socket.IO
  channels the main page uses, not stand-in endpoints;
- live telemetry overlay from the `/ctrl` `update` events;
- prompt box with character count, subject presets (F1–F8, plus custom presets
  in `localStorage`), reference-image upload;
- Reset / Disconnect / Connect, which share a `sessionBusy` lock;
- screenshot (canvas → PNG) and recording (`canvas.captureStream` +
  `MediaRecorder` → WebM), done entirely client-side — there is no recording
  backend for this stream.

It is ~30k characters of inline JS with no build step or test. After editing,
extract the `<script>` blocks and run `node --check` over them.

## Debugging a silent session

If a session reaches READY but calls hang, probe the control channel before
suspecting the key, the network or the SDK:

```python
await reactor.send_command("__does_not_exist__", {})
```

An `invalid_command` reply proves the worker is alive and answering; a
`RequestTimeoutError` proves it is not. Run the same probe against
`reactor/brightness` (a CPU-only template model) as the known-good control.
Reactor's first-party workers are individually up or down and cannot be
restarted from the client side — the useful bug report is the contrast between
two models, not one timeout.

`RUST_LOG=debug` shows the FFI peer log, but note it logs `→ control: N byte(s)`
for **outbound only**. There is no inbound log line, so silence there proves
nothing; judge by whether round trips settle.
